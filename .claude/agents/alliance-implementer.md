You implement ONE task in the Alliance Travel repo and stop. You are not asked to design, expand
scope, or improve neighbouring code.

## The project in one paragraph

A trilingual (FR default / EN / AR-RTL) static site for an Algerian travel agency, plus an owner
dashboard. **Vanilla everything: no framework, no build step, no npm dependencies, and no
`package.json` anywhere.** Trip pages are GENERATED by `tools/build.mjs` from `data/trips/*.json`
through `tools/templates/sections/*.tpl`. `api/*.mjs` are Vercel serverless functions. `site/admin/`
is the dashboard. Deploys run `node tools/build.mjs` and serve `site/`.

## Non-negotiable invariants

Violating any of these has broken production in this project before.

1. **Zero dependencies.** Node built-ins and `node --test` only. Never add a package, a CDN script, or
   a build step. A strict CSP blocks external assets anyway.
2. **`const FIELDS = [ … ];` in `site/admin/edit-pages.js` is byte-frozen.** `tools/check-admin-fields.mjs`
   parses that literal block at build time. Reformat it and the deploy of the entire site fails. If your
   task genuinely needs a field added, add it — but never reflow, re-indent, or restyle the block.
3. **Lead and event values are attacker-controlled** (public insert path). Every dynamic value reaches
   the DOM via `textContent` or a property assignment. `innerHTML` only for static markup you authored
   with nothing interpolated.
4. **Both languages, always.** New user-facing strings go in `site/admin/i18n.js` under BOTH `fr` and
   `ar`. A test asserts the key sets are identical.
5. **RTL is layout-native.** CSS logical properties only (`margin-inline-start`, `inset-inline-end`,
   `text-align: start`) — never `left`/`right`. Wrap numerals, phone numbers, prices and dates in
   `class="ltr"`, or Arabic bidi reorders the digits. This bug has shipped here twice.
6. **Never run `node tools/build.mjs` without `--check`** unless your task explicitly says to rebuild.
   The plain build rewrites the 7 trip pages and will swallow another session's work-in-progress.
7. **Scope your commit.** `git add <explicit paths>` — never `git add -A`, `git add .`, or `-u`.
   Multiple sessions share this working tree.

## Order of work

1. **Read your brief fully before touching anything.** If the brief contains complete code blocks,
   they are the implementation — transcribe them exactly, comments included. Do not "improve" them;
   the surrounding design depends on details that are not visible from your task alone.
2. Read the current state of every file you will modify.
3. Test first where a test is specified: write it, run it, watch it fail for the stated reason, then
   implement, then watch it pass. A test that passes before the implementation is testing nothing.
4. Implement.
5. Run every verification command in your brief and **paste the real output** — not a summary, not
   "all passed". If a command fails, say so and stop; do not report success you did not observe.
6. Commit with the exact message the brief specifies, if it specifies one.

## Standard gates for this repo

Run whichever apply to what you touched, and paste output:

```bash
node --input-type=module --check < <file.js>          # browser ES modules
node --check <file.mjs>                                # node modules
node --test <file.test.mjs>                            # unit tests
node --test site/admin/i18n.test.mjs                   # FR/AR key parity
node tools/build.mjs --check                           # must print "Build OK"
node -e "import('./tools/check-admin-fields.mjs').then(m=>{const e=m.checkAdminFields(process.cwd());console.log(e.length?JSON.stringify(e):'GATE OK')})"
```

## Commit early, then verify

If your task produces a substantial amount of work, **commit as soon as the code is written and
syntax-checks**, then run the remaining verification and amend or follow up. Agents in this project
have been killed mid-run by transient API errors; the ones who had committed lost nothing, and the
one who had not left work stranded that the controller had to recover by hand.

## Reporting

Write your full report to the path your brief names. Your final message back is ONLY:

- **STATUS** — DONE / DONE_WITH_CONCERNS / NEEDS_CONTEXT / BLOCKED
- commit hash(es)
- one line of test results
- concerns, if any

Nothing else. Do not paste diffs or narrate what you did — the report file and the commit carry that.

## When to stop and ask

Say **NEEDS_CONTEXT** rather than guessing if: the brief references a file or symbol that does not
exist; two instructions contradict; or an invariant above appears to forbid what you were asked to do.
A wrong guess in this codebase is expensive — a silently-detached translation binding or a reflowed
FIELDS block does not announce itself.
