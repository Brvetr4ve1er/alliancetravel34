# Arabic Translation Coverage Audit — Alliance Travel

**Branch:** `refactor/trim-v26`  ·  **Date:** 2026-06-03  ·  **Status:** READ-ONLY audit (no code changed)

## TL;DR

The i18n engine works correctly and the FR/EN/AR dictionaries are well-formed.
The **gap is structural, not engine-level**: only **3 surfaces** were systematically annotated with
`data-i18n` — top nav, footer, and the home page body. The five trip pages, the `/voyages/` index,
and `/404.html` have annotated **nav + footer only** — every visible body section (hero copy, day
itinerary, highlights, inclus/non-inclus, FAQ, hotel cards, calculator, related-trips, final CTA)
stays in baked-in French regardless of the switcher state. That is exactly what users see when they
flip to AR: the chrome (nav, footer) flips to Arabic, the page content does not.

## Section B — Root Cause Analysis (≈200 words)

The wiring pass that produced the current 178 attributes evidently followed a **shared-chrome-first**
strategy: the developer started with `<nav>` + `<footer>` + the home-page hero/sections (all of which
have well-defined namespaces in the dictionary), then stopped — probably because the trip pages each
have ~70-150 unique strings without dictionary entries, and bulk-annotating them requires both a
schema decision (per-trip namespaces vs. shared `trip_page.*`) and ~500 net new dict entries × 3
languages. That work was never scheduled.

Secondary causes:

1. **No dictionary entries for trip-page-specific content.** Even the shared trip-page keys
   (`trip_page.itinerary`, `trip_page.included`, etc.) exist as labels but no HTML element uses
   them — they were added speculatively. The per-trip body strings (hotel names, FAQ answers, day
   itineraries, hero leads) have no entries at all.

2. **`scroll-hero.js`-painted strings are double-blind:** the hero text comes from `data-*` attributes
   that the i18n engine doesn't scan (it only looks at `data-i18n*`). Even if a key existed,
   the engine wouldn't replace them. Net effect: AR users see French hero titles.

3. **`/404.html` lacks `<nav class="site-nav">`,** so `buildSwitcher()` silently no-ops at line 779 and
   the user gets stuck in whatever language was active when the page was reached.

4. **No `:lang(ar)` selectors** are at fault — the engine sets `<html lang>` + `<html dir>` correctly
   (line 663). Punctuation/RTL is working where keys exist; the symptom is "no key, no swap".
